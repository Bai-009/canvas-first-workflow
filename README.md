# Canvas-first Workflow

这是一个独立于公司生产代码的共同设计项目。目标不是先做出一个能演示的页面，而是逐步验证：怎样让画布成为 AI 生成工作流的核心载体，并让背后的 Agent 架构真正支撑这种交互。

## 这份 README 怎么使用

这是一份持续生长的设计记录。

- 只有双方已经明确确认的结论，才会写入“已确认的决定”。
- 尚未讨论清楚的内容，放在“下一步待决定”，不提前当成方案。
- 如果后续发现原决定有问题，保留修改原因，不让新结论悄悄覆盖旧前提。
- 仓库中现有的 Schema、样例、校验代码都只是前期草稿，目前不代表已经确认的最终设计。

## 已确认的决定

### 第一步：选择一条真实 Query 作为共同设计对象

我们不先抽象讨论完整架构，而是让一条具体 Query 依次经过 Plan Agent、外部机制、执行 Agent 和画布，以此检验每一个设计决定。

当前测试 Query：

> 每天读取新增合同，解析内容，抽取关键字段并写入合同表。

### 第二步：确定 Plan Agent 的核心职责

Plan Agent 不是把用户的话机械地拆成几个步骤。它承担架构师的职责，首先要端到端理解用户想完成什么，再据此设计处理路径。

对于当前 Query，Plan Agent 首先形成的意图理解是：

> 建立一个每天运行的合同入库流程：识别新增合同，解析合同内容，抽取关键字段，并将结果写入合同表。

当前输入还不完整，至少没有说明具体抽取哪些字段、写入哪一张具体表。因此它不能假装需求已经闭环；但已有信息足以形成一份部分计划，也不应该直接阻塞。

当前结论是：

- Plan Agent 先建立端到端的意图理解，步骤是这个理解的展开，不是起点。
- 它要把“已经理解的内容”和“仍然缺失的信息”同时反馈给用户。
- 当前需求状态应是 `partial`，而不是 `ready` 或 `blocked`。
- Plan Agent 负责规划处理路径，但不负责搜索或选择具体 WorkItem。

### 第三步：Plan 是共同理解，不只是步骤列表

Plan 同时服务用户界面与后续系统。它至少需要表达端到端意图、处理路径、尚未解决的信息和当前完整度，让用户能够纠正 AI 的理解，也让后续执行不会重新猜测用户意图。

对话框是用户进入 Plan Loop 的交互通道，不是最终结果的载体。用户在对话中确认的信息必须写回结构化 Plan，不能只留在聊天记录里。

### 第四步：重大缺失通过卡片与用户交互

Plan Agent 可以使用受限的只读查询与用户交互工具。遇到输入来源、处理目标或输出位置等重大缺失时，可以向用户展示选择卡片、填写卡片或确认卡片。

用户可以回答，也可以跳过。跳过不代表问题已经得到回答，更不允许 Agent 虚构不存在的目录、数据表、字段或处理方式。卡片的作用是提高首次生成的准确率，而不是强迫用户一次提供完整需求。

### 第五步：先生成节点骨架，具体逻辑延后绑定

当处理路径已经明确，但 SQL、Python 等节点的具体逻辑尚未说明时，可以先建立真实节点及其上下游关系，不生成一段看似完整但依赖虚构字段或表名的代码。

这类节点需要显式标明内部逻辑仍待补充。用户之后可以选中具体节点，在节点级对话中描述完整处理逻辑；Agent 再结合该节点的真实上游数据结构、下游目标和用户说明生成代码。这样可以保留已经形成的画布结构，并降低后续修改成本。

### 第六步：Plan 输出全局计划与结构化步骤任务书

Plan Agent 不直接为每一步编写一段不可校验的最终 Prompt。它输出一份全局 Plan，并为每一步生成结构化的步骤任务书。

状态机负责按照当前步骤组装执行 Agent 的实际上下文。执行 Agent 每一轮都能看到完整 Plan，避免只顾当前步骤而失去全局目标；但单轮只负责实现当前步骤。

执行 Agent 的上下文由以下内容组成：

- 稳定的 System Prompt、工具定义和输出格式；
- 完整 Plan；
- 当前步骤任务书；
- 前序步骤已经生成并确认的节点、配置和数据结构；
- 用户已经确认的约束；
- 尚未解决的信息，以及禁止擅自推断的内容。

用户首次描述不必完整。Plan Loop 通过后续对话与卡片不断补充同一份 Plan，状态机始终以当前已提交的 Plan 为准，而不是要求执行 Agent 重新阅读整段聊天记录。

### 第七步：根据描述完整度产生可用实现或骨架

首轮生成允许得到两种诚实的结果：

- 用户已经把必要信息描述清楚时，生成配置完整的工作流，并在通过必要校验后进入可运行状态；
- 信息不足但已经能够判断处理结构时，先生成节点与连线骨架，明确告知用户它还不能真实使用，以及仍需补充哪些内容。

骨架不是失败结果，也不能伪装成已经完成的工作流。它是下一轮交互的基础：用户选中尚未完成的具体节点，继续通过 Prompt 描述处理逻辑，Agent 再结合该节点的真实上下文补充实现。

Plan 的 `partial` 表示用户意图仍不完整；画布中的骨架状态表示具体实现仍未达到可运行条件。两者相关但不是同一个状态，系统和界面不能混用。
