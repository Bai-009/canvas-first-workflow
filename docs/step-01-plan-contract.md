# 第一步：最小 Plan 契约

## 目标

第一次用户输入通常并不完整。本阶段不要求 Plan Agent 猜出完整工作流，而是要求它同时交付：

1. 当前已经能够确定的处理路线；
2. 当前需求的完整程度；
3. 用户还需要补充什么，以及缺失信息影响哪些步骤。

Plan 是一个可修订的处理意图，不是可执行 DSL。

## Plan Agent 能决定的内容

- 用户的整体目标；
- 步骤标题与步骤意图；
- 步骤之间的依赖；
- 用户明确提出的约束；
- 当前仍然存在的开放问题。

## Plan Agent 不能决定的内容

- WorkItem 名称、版本和候选；
- 节点参数、连线和画布位置；
- 机器级输入输出契约；
- 某一步是否已被前序节点实际覆盖；
- Plan 或 Graph 的正式 ID、版本和执行状态。

## 完整程度

- `ready`：当前没有需要用户回答的开放问题，可以进入执行阶段。
- `partial`：已经能形成部分处理路线，但仍有问题影响一个或多个步骤。
- `blocked`：连可靠的部分路线都无法形成，必须先获得用户信息。

`readiness` 是模型提出的判断，不是最终系统事实。Plan Gate 只校验它与输出结构是否自洽；后续的产品策略才能决定 `partial` 是执行稳定前缀还是先等待用户。

## 模型输出与系统状态

模型使用本轮临时 `ref` 表达依赖。Plan Gate 通过后，系统再分配稳定的 `planId`、`stepId` 和 `planVersion`。

步骤运行状态、节点映射和画布进度属于系统状态，不写入 `PlanProposal`。前端渲染已提交 Plan，而不是模型尚未校验的原始文本。

## 本阶段能够校验的内容

- JSON 结构和字段类型；
- 步骤引用是否存在且唯一；
- 依赖是否自指或成环；
- 开放问题是否引用真实步骤；
- `ready`、`partial`、`blocked` 与步骤、问题数量是否自洽；
- 模型是否越权输出了未定义字段。

本阶段不能证明 Plan 的语义拆解是最优的，也不能证明平台一定存在对应能力。这些结论只能在执行阶段依据真实能力和后端校验逐步形成。
