# 状态机

状态机管的是：一份东西从用户的话走到画布，每一步谁在动、动完沉淀了什么。Plan 阶段的那一半做出来了（[src/plan-session.mjs](../src/plan-session.mjs)），执行阶段的那一半是草稿，逐条待确认。

## 一条总规则：回合制

任何时刻只有一方在动。用户发一句，模型跑，用户等；模型回来，轮到用户。用户敲定方案按开始，执行者跑，用户不动；用户想动，先按停。

停止是一个明确的动作——发送键变成停止键——不能从「用户又打了字」推断出来。手滑打的字会把正在跑的一轮作废，还逼模型去读一句垃圾。

回合制替掉了早先设计的乐观并发（requestId、基线检查、过期丢弃）。那套机器解决的麻烦是两方同时动；两方从不同时动，它就没有出场理由。

## Plan 阶段（已做）

持有三样：对话记录、过了闸门的每一份方案（最后一份是当前方案）、这一轮跑没跑着。

规则一条：**当前方案只在新的一份过了闸门时才换。** 只说话的一轮、被停掉的一轮、几次都没过闸的一轮，都不碰它。

一轮的四种收场，都回到用户：

- 只说话没提交：记录多了它这句，方案不动。
- 方案过闸：记录多了工具调用和回执；当前方案换新，版本加一，上一版留着给界面按编号算增量。
- 几次都没过闸：这轮的往返不进记录，只留用户那句，方案不动，报错。
- 用户按停：同上，不报错。

代码：`createPlanSession` 的 `say` / `stop` / `currentPlan` / `revision`；两版之间的差异由 `diffPlans` 按编号算（沿用、原地改、新增、消失）。测试守着「只在过闸时换」「跑着不收第二句」「停掉只留用户那句」「第二轮交给模型的记录带着第一轮的工具调用和回执」。多轮命令：`npm run plan:chat`。

## 执行阶段（草稿，逐条待确认）

已经确认的三条：

- **执行者没有跨步骤的上下文。** 每一步的上下文由状态机从账本临时组装：完整方案、这一步、当前画布、前序节点的实际输出、已确认的事实、挂在这一步上的用户指示。一步做完、改动过闸门原子提交，那一步的对话就完成使命。所以暂停只可能损失正在做的这一步，而它本来就还没提交。
- **方案改了不回滚，从头对账。** 状态机从第一步重新走，每一步执行者看着画布上已有的东西判断「已覆盖」还是要改。哪一步受影响是语义判断，留给执行者，不由程序比字符串。行业叫法：reconcile；重跑不改变已经对的东西叫幂等。
- **两个入口由用户指着决定。** 主输入框说的话是对整条链说的，走 Plan Agent，出新方案；在节点上说的话是对这一个节点说的，走执行者，范围锁定这个节点，方案不动。节点级的一轮沉淀两样：节点上的改动，和这条指示本身。指示挂在步骤编号上而不是节点上，节点重建时它还在。节点上说的话如果其实改的是链路形状，执行者交回 `replan_required`，转去走 Plan Agent。

讨论中列过、还没逐条确认的换手：

- 按开始：前提是有当前方案，partial 也行；执行者从第一步对账。
- 执行者每一步的收场：改动过闸 → 提交、下一步；已覆盖 → 记下、下一步；最后一步做完 → 轮到用户；要问用户 → 问题挂在这一步、轮到用户，答了再按开始，从头对账；平台没这个能力 → 缺什么挂在这一步、轮到用户（第一版不自动找路）；发现剩下的方案走不通 → 它的发现作为一条消息进对话记录、Plan Agent 出新方案给用户看、不自动接着执行；用户按停 → 这一步作废、画布停在上一次提交。
- 四条不变量：方案只在过闸时换；画布只在过闸时改；执行只由用户按开始启动，方案一换版本就得重新按；每次按开始都从头对账。

挂账：平台没能力时的自动找路；用户手改节点走不走闸门；几次没过闸的往返要不要留一点给下一轮当教训。
