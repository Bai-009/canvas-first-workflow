# 观察

真模型跑出来的行为记录。few-shot 例子照着这里的真实失误写，不凭想象写。
原始输出在 fixtures/observed/。目前的观察都来自 deepseek-v4-pro。

## 2026-09-02 首轮,三个场景

场景:合同 PDF(非结构化)、"帮我搞个工作流"(没闭环)、ODS→DWD→DWS(结构化数仓)。

成立的:

- 两条分支都对。描述清楚的出 partial 骨架;没闭环的不调工具、只说话,
  反问的正是两个地基(手上什么形态、最后要变成什么)。
- 必问的判据落地了。四个问题全是"错了看不出来"那类:扫描件还是文本层、
  "新增"口径、抽哪几个字段、写哪张表。没有塞校验、监控、去重这类步骤。
- 数仓场景的 u3 明确写"给报表用是消费端,不构成一次形态转变"——推导纪律
  被执行,而且被说了出来。
- 同题重跑结构稳定:合同场景跑两次,步骤、问题、编号完全一致。

失分寸的(few-shot 的靶子):

1. 提交轮零说话。三次提交没有一次先说话,「提交之前说话」那节没被执行。
   只说话的轮次话说得很好,所以不是不会说,是调工具时不说。可能是厂商的
   工具调用习惯(content 留空),换别家模型对照后再定治法。
2. 步骤编号漂移。数仓场景步骤用了 ods_to_dwd 这种描述式命名(u/q 仍是
   u1/q1)。schema 的正则两种都放行。描述式命名的隐患:步骤内容一改名字
   就得跟着改,"沿用编号=原地改"的机制就不稳。约定该在 few-shot 里统一示范。
3. 打包提问。一条 openQuestion 里塞两问("哪些指标+什么粒度"、"增量还是
   全量+快照还是累计")。界面按条填答,一条一问才好落。

待拍板的分歧:

- 触发要不要独立成步。模型两个场景都把定时触发折进第一环的 input 里说明,
  不给它单独一步;我们手写的 fixture 里触发是独立的 s1。按"数据形态转变
  一次是一步"衡量,时间信号本身没转变数据形态,模型的切法反而更严。
  改 fixture 还是改约定,待定。
