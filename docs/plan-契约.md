# PlanProposal 契约

Schema 在 [contracts/plan-proposal.schema.json](../contracts/plan-proposal.schema.json)，Gate 在 [src/validate-plan-proposal.mjs](../src/validate-plan-proposal.mjs)。这份文件说的是各字段为什么长这样。

角色边界见 [架构.md](架构.md)。

## 这份契约要解决什么

用户第一次说的话通常不完整。这一层不要求 Plan Agent 猜出完整工作流，而是要求它同时交出三样：

1. 当前已经能确定的处理路线；
2. 当前需求的完整程度；
3. 用户还需要补充什么，以及缺失的信息影响哪些步骤。

Plan 是一个可修订的处理意图，不是可执行 DSL。

## 字段

### `readiness`

- `ready`：没有需要用户回答的开放问题，可以进入执行阶段。
- `partial`：已经能形成处理路线，但仍有问题影响一个或多个步骤。
- `blocked`：连可靠的部分路线都形不成，必须先拿到用户信息。

它说的是**能不能真实运行**，不是路线完不完整。路线完整、但关键信息缺失，只能生成骨架——那仍然是 `partial`。

`readiness` 是模型提出的判断，不是最终系统事实。Gate 只校验它和输出结构自不自洽。

### `goal`

端到端意图，一句话。步骤是这个意图的展开，不是起点。

### `understanding`

对用户原话的逐段理解，一条长这样：

```json
{ "ref": "u1", "quote": "每天", "reading": "每天定时触发一次" }
```

`quote` 是用户原话里的片段，用户拿它逐句核对——不是读一段 AI 复述的话去猜哪里读歪了。`reading` 是这一段被读成了什么。

**按原话切分，不按步骤切分。** 两者数量可以不同：合同那条 Query 里「解析内容」和「抽取关键字段」是两段原话，但在 `steps` 里合成一步。

用户在对话中确认的信息，更新到对应那条 `reading` 上，不另开一栏。早期草稿里有一个平铺的 `constraints` 字符串数组，已经删掉——它没有出处，用户无从核对，界面上也没有落点。

### `steps`

数据链路。**按语义处理划分，不按动作数划分。**

- `title` / `intent`：这一步要达到什么结果。不写用什么工具、怎么实现。
- `input` / `output`：这一步吃什么、交出什么。**语义层描述，不是机器契约**——写「一份合同一条的结构化记录」，不写字段名和类型。机器级的输入输出由 Execution Agent 在真实节点上确定。
- `dependsOn`：先后与依赖。

`output` 必填，`input` 在链路起点可以没有。定这两个字段是因为：如果 Plan 只给动词，每一步交出什么就成了 Execution Agent 边做边定的——第一步的执行决定输出是文件路径，第二步只能接路径；等第二步发现它要的是文件内容，第一步已经提交了，回不去。

一个 step 对应几个节点，由 Execution Agent 决定，可能是零个、一个或多个。

### `openQuestions`

用户还没说明的关键信息。

**列全，不预筛。** 哪些现在问、先问哪一个，是状态机的判断，不是 Plan Agent 的。`reason` 写的是「缺了它为什么说不清楚」，状态机拿这个去判断要不要现在停下来。

`affects` 指向受影响的步骤。

## Plan Agent 能决定什么

- 用户的整体目标；
- 对用户原话的逐段理解；
- 步骤的标题、意图、交付物与依赖；
- 当前仍然存在的开放问题；
- 当前需求的完整程度。

## 不能决定什么

- WorkItem 名称、版本和候选；
- 节点参数、连线和画布位置；
- 用一个节点还是三个节点；
- 机器级的输入输出契约、SQL 与 Python；
- 某一步是否已被前序节点实际覆盖——那是 Execution Agent 的 `covered`；
- Plan 或 Graph 的正式版本与执行状态。

Schema 用 `additionalProperties: false` 挡住这些，测试里有两条断言守着（`workItem`、`nodeCount`）。

## `ref` 的含义

`ref` 是模型给的编号，用来表达**跨版本的同一条**。

Plan Agent 每一轮吐一整份，不吐增量。它认为这次是小修，就沿用上一版的 `ref`；认为是推翻重来，就给新的。前端拿新旧两版算 diff：`ref` 沿用的那几条原地过渡，`ref` 全新的整栏重画。模型的判断直接变成界面的动作，不需要额外加一个「这次是小修还是重写」的开关字段。

所以系统不再给每一步另发一个稳定 ID——那会产生两套编号和一张映射表，而 `ref` 已经够用。系统分配的是整份 Plan 的 `planRevision`。

`ref` 沿用不保证内容不变，只表示模型认为这还是那一条。Gate 能看见两版之间哪些 `ref` 消失了、哪些新增了，但**不拦**——模型砍掉一条理解可能是对的，界面只要知道它没了，好演退场。

## 模型输出与系统状态

步骤运行状态、节点映射、画布进度属于系统状态，不写进 `PlanProposal`。

前端渲染的是已提交的 Plan，不是模型尚未校验的原始文本。

## Gate 在这一层能校验什么

- JSON 结构与字段类型；
- `ref` 是否唯一（`understanding` 与 `steps` 各自独立）；
- `quote`、`reading`、`output` 非空；
- 依赖是否指向真实步骤，是否自指或成环；
- 依赖了前序步骤的，是否说明了自己吃什么——没说就是链路在这儿断了；
- 开放问题是否引用真实步骤；
- `ready` / `partial` / `blocked` 与步骤、问题的数量是否自洽；
- 模型是否越权输出了未定义字段。

## 校验不了什么

- Plan 的语义拆解是不是最优的；
- 平台是不是真的存在对应能力；
- `input` 和上游 `output` 在语义上是否真的接得上——字符串对不上不代表接不上，反过来也一样。

这些只能在执行阶段依据真实能力和画布侧的校验逐步形成。Gate 只判定**能确定为假**的东西，判定不了的一律放行。
