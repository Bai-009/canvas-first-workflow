# 架构

四个角色各管什么，一份东西从用户的话走到画布要经过谁，谁在哪一步做裁决。

后面的字段设计、提示词、Gate 规则都以这份文件为依据。

## 四个角色

| 角色 | 负责什么 |
|---|---|
| **Plan Agent** | 像产品经理兼架构师。把用户意图变成完整的数据处理要求，指出缺口，定义每一步要达到的结果 |
| **状态机** | 像项目调度者。决定当前执行哪一步、什么时候暂停、什么时候询问用户、结果是否可以进入下一步 |
| **Execution Agent** | 像开发工程师。看到实际工具、WorkItem、已有画布和前序产出，自主决定如何实现当前目标 |
| **Gate** | 像测试与验收。检查节点、参数、连接和实际产出是否真的满足要求 |

一句话：

> Plan Agent 定义一条数据链路「应该完成什么、怎样才算完整」；Execution Agent 根据平台真实能力决定「具体用什么、怎么把它做出来」。状态机负责把前者逐步交给后者，并控制整个过程。

## Plan Agent 的边界

它需要判断：

- 输入是什么
- 数据经过哪些语义处理
- 最终输出什么
- 整条链路是否闭环
- 哪些关键信息用户还没说明
- 在信息缺失时，只能生成骨架还是已经可以真实运行

它不应该决定：

- 使用哪个 S3、目录或数据表
- 选择哪个 WorkItem
- 用一个节点还是三个节点
- SQL、Python 或参数具体怎么写

「不管数据具体从哪里来」不等于「不管数据来源是否明确」。来源没说清，属于「哪些关键信息用户还没说明」，Plan Agent 要指出来；但用哪个桶、哪个目录，它不碰。

这两张清单将来会直接进 Plan Agent 的系统提示词。进提示词时，「不应该决定」这四条要写成带理由的逻辑链，说明为什么不能这么做，不写成光秃秃的禁令。

## 一个例子

用户说：

> 每天读取新增合同，解析内容，抽取关键字段并写入合同表。

Plan Agent 该产出的是：

> 每日触发 → 获取新增合同 → 解析并抽取结构化信息 → 写入合同表。
> 当前缺少：如何判定新增、抽取哪些字段、输出位置是否已明确。

它不能产出：

> 使用 S3 Reader 节点 → PDF Parser 节点 → 编写一段 SQL INSERT。

后面这些属于 Execution Agent。它看到完整 Plan、当前要求、真实候选工具、已有节点和前序结果之后，可能用一个节点完成两步，也可能用三个节点完成一步；如果前面的节点已经覆盖下一步，它可以不再添加节点。

## Execution Agent 的边界

它不是「节点选择器」，是把计划目标落实成真实画布的实现者：

> Execution Agent 读取完整 Plan 和当前画布，在平台真实能力范围内，自主选择、组合并配置 WorkItem，产出一个可校验的画布改动，使当前处理目标得到实现。

### 每一轮它看到什么

状态机调用它时，要给它：

- 完整 Plan——理解全局终点，避免局部贪心
- 当前要落实的那一个 Plan Step
- 当前画布上已经有什么
- 前序节点的实际输出、Schema 和配置
- 用户已经确认的事实
- 仍然缺失、禁止猜测的内容
- 它能调用的工具，例如搜索 WorkItem、读取节点能力、查看真实 Schema

所以它不是一个看不到后面的外包开发。它知道全局设计，但本轮只负责推进当前目标。

### 它具体做什么

以「解析合同内容并抽取结构化字段」这一步为例，它会先看画布：

1. 前面的节点已经输出了什么？
2. 这个目标是否已经被已有节点覆盖？
3. 平台有哪些真实能力可以完成它？
4. 需要一个节点，还是多个节点组合？
5. 已知信息是否足以配置节点？
6. 产生的结果能否满足后续「写入合同表」的需要？

然后它可以搜索真实 WorkItem、查看候选节点的输入输出和配置要求、选择一个或多个节点、连接已有节点、填写有依据的参数、在 Schema 和需求明确时生成 SQL 或 Python，最后提交一份「建议如何修改画布」的结构化结果。

它不能绕过校验直接写入画布。外部 Gate 验证通过后，画布才真正长出这一段。

### 它不是机械地「一步加一个节点」

Plan 有三步，状态机会按三步调用它，但每一步都不强迫它增加节点。它可以判断：

- 当前步骤需要三个节点
- 一个节点同时完成两个步骤
- 上一步选出的节点已经覆盖当前步骤
- 当前步骤缺少必要信息，只能搭骨架
- 平台没有对应能力，需要返回 Plan 层调整剩余计划

所以某一轮成功的结果也可能是「当前目标已被节点 A 覆盖，无需增加节点」。这才是自主执行，不是照着 Plan 机械施工。

### 一次执行不是一次模型调用

一轮 Execution Agent Loop 可能是：

```
读取当前任务
→ 调用工具搜索 WorkItem
→ 查看候选节点详情
→ 查询真实 Schema
→ 选择并配置节点
→ 输出画布改动
→ end_turn
```

中间可能发生多次模型调用和工具调用，它们共同完成一个当前步骤。

### 它的合法输出

最终不返回一段话，而是返回这几类结果之一：

| 输出 | 含义 |
|---|---|
| `graph_patch` | 建议增加、修改、连接哪些节点 |
| `covered` | 已有画布已经完成当前目标 |
| `needs_user_input` | 缺少真实信息，不能继续猜 |
| `capability_missing` | 平台没有足够能力实现 |
| `replan_required` | 实际能力或前序结果使剩余计划需要调整 |

### 什么才算执行成功

不是「搜到了节点」，也不是「生成了 DSL」，而是：它提出的画布改动通过外部校验，并且有证据表明当前处理目标已经被实现，同时没有破坏完整数据链路。

Plan Agent 交付的是任务书；Execution Agent 交付的不是回复，而是画布的下一次真实生长。

## 主链路

两段。第一段把用户的话变成一份权威 Plan，第二段把 Plan 里的一步变成画布上真实长出来的一段。

### 从用户的话到一份权威 Plan

```
用户的话 + requestId
  │
  ▼
Plan Agent
  ├─ 系统提示词：职责、边界、禁止事项
  └─ 输出约束：PlanProposal Schema
  │
  ▼
一段 JSON 文本
  │
  ├─ JSON.parse 失败 ──▶ 确定性清理后重试；仍失败则回给模型重来
  ▼
validatePlanProposal
  │
  ├─ 校验失败 ────────▶ 把 errors 原样回给模型，最多重来两次
  ▼
requestId / 基线是否仍然有效
  │
  ├─ 已过期 ──────────▶ 丢弃。不渲染，也不执行
  ▼
提交 planRevision
  │
  ▼
权威 PlanProposal
  │
  ├──▶ 前端投影：understanding / steps / 缺口摘要
  └──▶ 状态机持有完整 Plan
```

三处容易做错的地方：

**「修复」是两种不同的东西，不能混。** `JSON.parse` 失败时，程序可以做确定性清理——剥掉 ` ```json ` 包裹、截掉尾部多余文本——它不猜内容。语义校验失败时，程序一个字都不能改，只能把 `errors` 原样回给模型重来。Gate 的错误信息本来就写成了人话（「步骤 s4 依赖了前序步骤，却没有说明它吃什么」），模型读得懂。做出一个「帮模型补字段」的修复器，就是程序替模型编内容。

**校验通过不等于可以用。** 模型跑那十几秒里，用户可能已经改了话。校验之后还有一次提交判断：这个 requestId 是不是最新的、基线有没有变、能不能分配新的 `planRevision`。过期的结果一律丢弃，不渲染也不执行。

**`openQuestions` 不等于前端卡片。** Plan Agent 把缺口列全，不预筛；前端可以展示「还有哪些信息未明确」；此刻要不要问、先问哪一个，是状态机的判断。卡片里的候选项——比如「写进哪一张表」要列出的表名——必须由平台真实查询产生，不能由模型填。

### 从一个 Plan Step 到画布长出一段

```
状态机：持有完整 Plan，指定本轮 currentStep
  │  组装七项上下文（见「Execution Agent 的边界」）
  ▼
Execution Agent Loop
  │  按需调用工具：搜 WorkItem / 看节点详情 / 查真实 Schema
  │  多次模型调用共同完成一个步骤
  ▼
ExecutionResult ── Gate(result + revision)
  │
  ├─ graph_patch ────── Gate(graph) + 原子提交 ──▶ 画布长出这一段
  │
  ├─ covered ────────── 校验覆盖证据 ───────────▶ 推进下一步
  │
  ├─ needs_user_input ─ 校验这个缺口确实影响执行 ▶ 状态机组织用户交互
  │
  ├─ capability_missing ─────────────────────── ▶ 状态机决定：回 Plan 找别的路径 /
  │                                                问用户接不接受替代 / 确实没路才报阻塞
  │
  └─ replan_required ───────────────────────── ▶ 把执行中发现的事实交回 Plan 层
```

三处容易做错的地方：

**五类输出都要过校验，不是只有 `graph_patch`。** 尤其 `covered`——模型说「这一步已经被现有节点覆盖了」，状态机不能直接信。它必须说明是哪些节点、哪些实际输出覆盖了当前目标，由程序检查。

**工具是按需用的，不是必经流水线。** 「搜 WorkItem → 看详情 → 查 Schema」写成一条箭头串联会误导：提示词照着写，模型就会为了走完流程而制造工具调用。第一眼看出目标已被覆盖，就该直接返回 `covered`；候选信息已经够了，就不必再查详情。

**`capability_missing` 不等于「做不出来」。** 它是一个经过检索得到的事实：当前平台没有能力按这个方式实现目标。拿到这个事实之后怎么办，是状态机的判断，不是执行 Agent 的结论。

### 两处裁决，一条铁律

两个 Gate 都要检查版本：

- Plan Agent 返回时，看用户的 Query 是否已经改变；
- Execution Agent 返回时，看 Plan 或画布是否已经被用户改过。

旧结果一律不能落到画布。

Gate 只判定**能确定为假**的东西，判定不了的一律放行。以 `covered` 的证据为例，程序能确定为假的是三样：证据里的 nodeId 不存在、那些节点不在当前画布上、它们的输出和下一步的 `input` 对不上。至于「这些输出够不够满足当前目标」——那是语义判断，程序验不了，仍然归模型。Gate 查前三样，不假装能验第四样。

一条铁律：

> 执行 Agent 拥有技术决策权，但不拥有结果裁决权。它提出实现，外部机制决定这个实现能不能成立。

## 一路上纠正过的几处偏差

记下来，避免被重新捡起来实现。

1. **缺口不由 Plan Agent 筛。** 讨论中一度按「这个缺口挡不挡路、该不该问」给缺口分类。那是状态机的判断——什么时候暂停、什么时候询问用户，写在状态机那一行。Plan Agent 只负责把缺口列全，不预先决定哪些现在问。

2. **`readiness` 说的是能不能真实运行，不是路线完不完整。** 讨论中一度据此认为合同 Query 应该是 `ready`、README 第二步判断有误。路线完整但关键信息缺失，只能生成骨架，仍然是 `partial`。README 第二步的结论不变。

3. **步骤边界按语义处理划分，不按动作数。** 「解析并抽取结构化信息」是一步，「每日触发」单列一步。

4. **排期不是 Plan Agent 的活。** Plan Agent 定义任务和依赖顺序，逐步调度归状态机。

5. **Plan Agent 不看工具库。** 讨论中一度提出把「能力轮廓」作为上下文喂给 Plan Agent，好让它判断某个缺口会不会换掉 WorkItem。这条作废——判断会不会换 WorkItem，本身就不是它的活。

6. **Execution Agent 可以把球踢回 Plan 层。** 讨论中定过「两个入口」——一个改动会不会改变计划长什么样，决定它走 Plan 还是直接交给 Execution Agent。那说的是**用户**发起的方向。`replan_required` 是 **Execution Agent** 发起的反向：它在平台真实能力面前发现剩余计划走不通，退回 Plan 层调整。之前没有这条路，Plan 一旦定了就只能往前。

## 本文之外、已经定下但还没落位的结论

- 用户在 Plan 阶段答完一句之后，Plan Agent 重吐一整份计划，不吐增量。每一条的编号（`ref`）沿不沿用上一版，由它自己判断：小修沿用，推翻重来就给新的。界面拿新旧两版算 diff——编号沿用的那几行原地过渡，编号全新的整栏重画。模型的判断直接变成界面的动作，不需要额外加一个「这次是小修还是重写」的开关字段。属于 Plan 契约，等字段那一摊开始时落位。

- Execution Agent 的输出契约还不存在。上面那五类输出是一个 tagged union，各自形状不同（`graph_patch` 带画布改动，`needs_user_input` 带问题，`capability_missing` 带缺什么能力）。它和 PlanProposal 平级，需要自己的 Schema 和自己的 Gate——画布侧的 Gate 查的是节点存不存在、参数合不合法、连接对不对得上、这一改有没有破坏已有的数据链路，和 Plan 侧的 Gate 查的完全不是一回事。
