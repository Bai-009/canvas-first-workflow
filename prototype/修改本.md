# 原型修改本

这个原型不从零写。基线是已经磨过三十多版的成品，之后的每一次改动都记在这里。

**V6 是概念，不是实现。** 它证明的是一种感受——工作流一个一个长出来，轻，留白，随手能改。它不证明架构，也不证明里面的数值。

代码里两类东西要分开看：

- **带注释的，是撞过墙留下的判断**：`RESERVE = 344`（右上角需求框占掉的一条，展开的卡片不能钻到它下面）、`CPS / NL_REST / BLANK_REST`（打字节奏）、`MAX_CODE_LINES = 18`、`.task-foot` 的高度必须用 JS 量出来写进 `--foot-h`（写死数字会把 padding 和分隔线算进去，文字被裁）。这些不写下来就会丢。
- **光秃秃的，是当时随手定的**：`TILE 176` / `GAP 260` / `OPEN_W 540` / `BASE_Y 96, AMP 48` / `CODE_LH 19` / `CODE_PAD 26`。别当依据，该改就改。

同理，`nodeX(i) = i * PITCH`、连线在节点之间画——这些是让演示跑起来的做法，不是对布局或架构的判断，不能拿来否定别的方案。

**记什么**：改了什么、为什么改。「为什么」是这本子唯一不可替代的部分。

### 2026-09-01 加入 Plan 阶段

**改了什么**

- `index.html`：新增 `.plan` 一套样式（插在 `.zoom` 之前）和 `#planCard` 结构（插在 `.zoom` 之前）。V6 原有样式一行未动。
- `workflow-rebuild-v6.js`：
  - `TASK` 换成信息不全的那一句「每天读取新增合同，解析内容，抽取关键字段并写入合同表。」
  - 新增 `PLAN` 数据常量、`flyToPlan` / `buildPlan` / `answerPlan` / `flyPlanToTask` 四个函数。
  - `run()` 里把 `flyTask(token)` 换成这四步；`reset()` 里补上 Plan 卡的复位。
  - `flyTask` / `showTaskInstant` 保留未动，`skipToEnd` 仍走原路。

**为什么**

- **换 Query**：原来那句（S3、字段、每天 8 点全说了）走不到 Plan 这一段——缺的东西正是这一段存在的理由。缺的部分由 Plan 里的一轮对话补齐，补完正好落到原有 `STEPS` 演的那条流上。
- **Plan 占画布中央**：画布还空着，注意力本来就在这儿。用户在底部打字，变化发生在他正看着的这张卡上——「你看着什么，就改什么」。
- **同一张卡换形态，不是换图**：`.plan-label` / `.plan-text` 和 `.task-label` / `.task-text` 的字号行高完全一致，飞行按这两块文字的左上角对齐算位移，落位时那两行一个像素都不动。
- **收窄 → 停一拍 → 飞**：两个几何动画不叠在一起。这是 V6 自己的规矩（见 `T` 那段注释：「同一张卡上两个几何动画重叠，节点从来没有真正落定过」）。
- **路线画成文字接箭头，不是四个方框**：步骤数不等于节点数，位置也还不知道。画方框等于预告「会有四个节点在这四个位置」，那是撒谎。路线只表达先后和依赖，那才是 Plan 这时候真正确定下来的东西。
- **只问两个问题**：不知道就挑不出工具的才问（读取来源、增量判定）。字段清单、目标表挑得出工具、只是填不满格子，不问，留成节点上的空格。

**这一版里哪些是可以随便推翻的**

版式全部是拿 V6 的 token 拼的（`--paper` / `--line` / `--ink` / 16px 圆角 / 同一组阴影），但分栏宽度、箭头串、分隔线这些排布是临时决定的，没有依据，该改就改。

### 2026-09-01 Plan 阶段改成真实节奏

**改了什么**

- 新增 `TP` 时长表，和 V6 原有的 `T` 分开。`TP` 的基准是**真实节奏**，不是演示节奏。
- `buildPlan` / `answerPlan` 重写：内容改成一条一条落（`dropRows`），不再整块淡入；块与块之间留真实停顿；回答之后先有一段「在看这两个答案改变了什么」，再逐行改写理解那一栏。
- 说完「开始」之后也留一拍，不是话音未落就飞走。
- `index.html` 加 `.drop` / `.swap` 两个动画，`.plan-body` 允许滚动（内容是逐条加进去的，高度一直在变）。

**为什么**

上一版把**演示速度当成了基准速度**，1× 是假的。真实场景里 Plan Agent 出一份计划要十几秒，而且不会整块闪出来。现在 1× ≈ 21 秒（不含打字和两次飞行），想看快的按 4×（≈5 秒）——`SPEED` 那套本来就在，所有等待都除以它。

几个具体的判断：

- **最长的那一段是「什么都还没有」的那一段**（`TP.land + TP.think1` ≈ 3.5 秒）。那正是最需要有形态的地方，所以它不是空白，底下那行字在说现在正想什么。
- **结构化内容一条一条落**：真实的流式输出解析出一条就渲染一条，观感本来就是这样，不是一块一块闪。
- **回答不立刻生效**：先「在看这两个答案改变了什么」停 2.2 秒，再划掉问号、逐行改写。否则用户会以为那两句话没被认真读。
- **理解那一栏是逐行改写**，先淡掉再换字——看得见是**这一行变了**，不是整栏重画。哪几行没变也看得见。

### 2026-09-01 文案按 V6 的尺子重写

**改了什么**

| 原来 | 现在 |
|---|---|
| 我是这么理解的 | 理解 |
| 处理路线 | 路线 |
| 这两件不问就动不了 | 待确认 |
| 「现在能做到哪一步」整节 | 删掉，并进状态行 |
| 先看清楚你要什么 | 正在理解需求 |
| 这件事要经过几步，每步之间怎么依赖 | 正在规划路线 |
| 哪些现在就必须知道，哪些可以边做边补 | 正在核对缺失 |
| 在看这两个答案改变了什么 | 正在更新计划 |
| 上面两个答完，就能开始搭。 | 4 步 · 2 项待确认 |
| 挡路的都清了，可以开始搭骨架。 | 4 步 · 待确认已清 |

理解栏右列统一成「…未定」收尾。用户自己说的两句保持口语，那是对的。

**为什么**

上一版是拿讨论时的说话方式当界面文案。这两套标准完全不同：讨论要把机制讲透，界面只标注内容。

V6 自己的文案就是尺子——`需求` / `已生成 6 步 · 每天 08:00 运行` / `正在修改 · 文档解析` / `描述你要做的数据处理`。**名词、极短、不拟人、不解释为什么。** 没有一句以「我」开头，没有一句在说设计意图。

三个具体的毛病：

- **拟人加讨好**：「我是这么理解的」。产品界面上 AI 用第一人称自述，读起来像客服机器人。
- **把设计意图贴到脸上**：「这两件不问就动不了」是我们讨论出来的判断依据，用户不需要知道，他只需要知道要答什么。
- **讨论用语当文案**：「挡路的」是我在对话里用的词，直接搬进了界面。

顺手删掉一整节：「现在能做到哪一步」那段解释性文字，是我在讲设计意图。状态行一句事实（`4 步 · 2 项待确认`）就够了，卡片高度从 575px 降到 488px。

### 2026-09-01 右上角卡片可展开：台前调度式的交换

**改了什么**

- `index.html`：`#world` 外面包了一层 `#stage`，专门承载「后退」——不碰 `world` 的相机 transform（`applyCam` 是直接写 `world.style.transform` 的，CSS 再加一个 transform 会打架）。新增 `.stage.recede` / `.task.live` / `.plan-close` 三组样式。
- `workflow-rebuild-v6.js`：新增 `arcFrames` / `openPlanFromTask` / `closePlanToTask` / `ensurePlanContent`。需求框落位后加 `.live`，点它展开；卡片上多一个「收起」。`reset` 跟着复位。

**为什么**

参照 macOS 的台前调度。它的关键不是「点开一个面板」，是**两个东西同时动，一进一出，读起来是一次交换**——不是先消失再出现。所以点需求框的那一拍里，卡片飞回中央，画布同时往后退（缩 4.5%、降到 30% 不透明、2px 模糊）。

**退的是深度，不是平面。** 这一条顺手解决了之前挂着的一个问题：我担心「工作流退场再入场，会掩盖局部修改的范围」——明明只改了抽取那一步，六个节点一起重新入场，看起来像全推倒了。现在工作流根本没走，它留在原位一个像素没挪，只是退到后面。改完前进回来，**只有真正被改的那个节点是变了的**，那条「节点身份延续则原地更新」才看得见。

飞行途中只动 `transform` 和 `scale`，不改宽高；真正的展开（`.open` 那次高度变化）等落位后走一拍。这是 V6 自己的规矩——同一张卡上两个几何动画不叠。台前调度能一边移一边长，是因为它的缩略图是张截图，纯 scale 不重排；这里的卡片两端都要能读，所以只能分两拍。

**顺带修一个 bug**：「跳到完成态」走的是 `showTaskInstant`，从来没跑过 `buildPlan`，Plan 里是空的，展开出来只有一个「需求」标签和一条状态。补了 `ensurePlanContent`——为空时按已答完的那一版填上。`reset` 里要把 `planText` 清掉，否则重新演示时它以为已经填过。

### 2026-09-01 「开始」从一句话改成一个入口

**改了什么**

- 新增 `.plan-go`「开始生成」，落在卡片底部状态行右侧（和「收起」同一个位置，按阶段互斥出现）。
- 两个待确认项**答完之后它才出现**；出现时带 `drop`。演示里停 1.5 秒让人看清入口在哪，再「按下」，然后才飞走。
- 删掉 `PLAN.go`，不再打字说「可以了，开始吧」。
- 输入框 placeholder：Plan 阶段「回答上面待确认的问题」，答完改成「还想改点什么」。

**为什么**

上一版靠用户打字说「可以了，开始吧」才相变，两处不对：

- **「开始」是个动作，不是一句要打出来的话。** 让人把一个动作说成一句话，本身就别扭。
- **提示不足。** 屏幕上没有任何东西说明现在能开始了，用户凭什么知道要说那句。

现在按钮**答完才出现**，出现这件事本身就是提示，不用再写一句「现在可以开始了」。反过来，问题没答完就没有入口——这也是诚实的：那两个是「不问就挑不出工具」的，不答真的搭不出骨架。用户看到两个亮着的问号、看不到开始按钮，自然知道先答哪个。

placeholder 也跟着换阶段。V6 原来的写法是祈使句（「描述你要做的数据处理」「描述你要改的地方」），这里沿用。

### 2026-09-01 展开/收起的四处跳变

不是手感问题，是四个能指出位置的跳变。

**一、收起时开头弹一下。** 反向动画是 `arcFrames(...).reverse()` 做的——`reverse()` 只翻帧的顺序，不翻 `scale` 的方向。于是收起从 `scale(.86)` 起步，而卡片当时是 `scale(1)`，第一帧就跳。改成 `arcFrames(x0,y0,s0, x1,y1,s1, cx,cy)`，起点终点都写全，不再靠 reverse。

**二、交接处有一帧是空的。** 原来 `taskCard.hidden = true` 瞬间抹掉，plan 卡从 `opacity: .2` 淡入——中间那一帧，一张已经没了，另一张还只有两成。改成两张在同一处重叠交接：plan 直接以不透明度 1 压上来，task 在底下淡出。视觉上是「卡片变宽了」，不是「一张换成另一张」。

**三、动画在 90% 处被 cancel。** `await wait(dur * 0.9)` 之后 `cancel()` 再写最终 transform，等于从 90% 直接跳到 100%。改成 `await anim.finished`，走满再收尾。正向那次 plan → task 的飞行也有同样的毛病（`wait(T.fly * 1.05 * 0.92)`），一并改了。

**四、飞行和展开完全分离，读成三段。** 飞过去 → 停 → 长大。现在飞到 55% 时就加 `.open`，位置和高度有重叠，是一个连续动作。

第四条要不要叠，V6 那条「一拍只干一件事」的规矩得看清楚它防的是什么：原文是「出生弹簧还剩 150ms 就开始撑宽高，同一张卡上两个几何动画重叠，节点从来没有真正落定过」——**防的是弹簧回弹没停就撑**。这里的位移曲线 `cubic-bezier(.32,.94,.28,1)` 没有回弹，前段很快，走到六成已经基本到位，这时候让高度接着长不会「没落定」。规矩的理由成立，规矩的字面不该照搬。

台前调度能一边移一边长大，是因为它的缩略图是张截图，纯 scale 不重排。这里两端都要能读，所以宽度那一跳只能靠重叠掩盖，不能靠缩放消掉。

### 2026-09-01 展开改成形变，不再是两张卡互换

**问题不在过渡曲线，在 t=0 那一帧。**

上一版的做法是：plan 卡（560 宽、文字按 560 重排过）直接摆到需求框的位置，需求框淡出，然后飞。于是第一帧就是 320 宽的卡被一张更宽、行数都不一样的卡顶掉——**那是替换，不是变形**。后面飞得再顺也救不回来。

V6 原来那套「按文字左上角对齐 + 淡入」为什么成立：那次是**输入框里的一句话**变成一张卡，两端本来就是不同的东西，用户认「同一句话换了身份」这个叙事。但右上角那张**已经是卡了**，再换一张卡进来就只能读成故障。

**改法：同一个元素形变。** `left` / `top` / `width` / `padding` / 正文 `max-height`，同一条时长、同一条缓动，一起走。

- 初态**逐项贴合**右上角那张卡——同样的 padding（`.plan.mini` 用 `13px 15px 12px`）、同样的宽度、同样的位置。此刻两张卡完全重合，换手看不出来。
- 终态先量后用：先展开量出高度和落点，再摆回初态，然后开闸。
- 形变期间**钉实测像素**，不用 `left:50% + translate(-50%,-50%)`——那套在宽高变化时自己也在移动，和形变叠一起算不清。
- 时长通过 `--mo` 传给 CSS，`SPEED` 一改跟着缩，不会提速后编排就散。

文字会在宽度变化时重排，这个消不掉（两端都要能读，就不能靠 scale）。但**一个元素连续变宽时的重排，和两个元素在同一位置对调，是完全不同的两件事**——前者是形变的一部分，后者是故障。

**顺手修正「画布中央」**：之前是整屏居中，卡片会被顶栏和底部输入条挤偏。现在按这两条让开，居的是画布可视区的中。

### 2026-09-01 收起：右侧塌陷的 bug + 点外面就收

**右侧那个 bug 的成因**

`sizeFoot()` 是靠临时加 `probe + landed` 量高度的，量完**两个一起摘**：

```js
taskCard.classList.add("probe", "landed");
taskCard.style.setProperty("--foot-h", taskFoot.offsetHeight + "px");
taskCard.classList.remove("probe", "landed");   // ← landed 也没了
```

V6 原来的顺序是「先 `sizeFoot()`、后 `add("landed")`」。我在 `closePlanToTask` 里写反了，于是 `landed` 刚加上就被摘掉，`.task-foot` 永远停在 `height: 1px; opacity: 0`——「已生成 6 步 · 每天 08:00 运行」连同右边的「查看引擎节点」整条都不见了，卡片还矮了 39px。看着就是右下角缺一块。

**教训**：V6 里带副作用的工具函数（`sizeFoot` 这种量完还原的），调用顺序是有讲究的，照抄调用不看它做了什么就会踩。

**收起的入口**

原来只有「收起」那一个字。现在点卡片以外任何地方都收，Esc 也收。开卡那一下也会冒泡到 document，但 `planOpen` 要等 `openPlanFromTask` 走完 await 才置真，所以不会开了立刻又关。

### 2026-09-01 收起时的「白色长条」

**成因**

`max-height` 是**上限**，不是高度。正文实际高 = min(上限, 内容高)。

收起时宽度 461 → 320，**内容重排会变高**——理解那个两列网格、待确认那两段说明，在 320 宽下都要多折好几行，正文自然高度从 358 涨到约 530。而旧代码的上限写的是 `70vh`（视口 783 时 = 548），前三成时间里上限一直大于内容高，于是正文**跟着内容一起先长高**。这时位置和宽度已经在 ease-out 的快段冲到位了——卡片贴上右上角、已经收窄，高度反而涨了：又高又窄的白板。

**改了三处**

1. `max-height` 从 `70vh` 改成**实测内容高度**（`planBody.scrollHeight`，上限取视口 62%）。上限不再高于内容，正文就不会先长。
2. **卡片高度改成显式动画**：`height` 进 `.plan.morph` 的 transition，两端都用实测值（展开态由 `planCenterRect()` 回传，收拢态取需求框实测高）。内容怎么重排都顶不动卡片的盒子。
3. `.plan.morph` 加 `overflow: hidden`，形变期间内容只被裁，不外溢。

**顺带记一条工具限制**

我这边的浏览器面板是隐藏的，**CSS 过渡和 rAF 都不推进**，`getBoundingClientRect()` 拿到的一直是过渡的起始值。所以「卡片停在 320 宽不动」这类测量结果全是冻结画面，不能用来判断动效。换禁缓存的服务器复测过，结果一样——不是缓存问题。

**动效只能在真浏览器里看。** 这边能验的只有：渲染结构、静态排版、控制台报错、以及像上面这种可以从 CSS 语义推出来的机制问题。

### 2026-09-01 收回瞬间卡片不完整

`.task-foot`（状态栏那一条）有一条 400ms 的高度过渡。`closePlanToTask` 里 `add("landed")` 之后立刻 `getBoundingClientRect()`，量到的是**还塌着**的 87px，不是最终的 126px。

于是 plan 卡一路收到 87 高就停了，换手时换上一张 126 高的需求框——**底下那 39px 晚一拍才长出来**，看着就是「先不完整，等一下才完整」。

改法：整个形变期间需求框是 `opacity: 0`，状态栏没人看，所以量之前先 `taskFoot.style.transition = "none"`，让它瞬间到位，量完再还原。

和上一条右侧塌陷是同一个根因的两面：**`.task-foot` 的高度既受 `landed` 类控制，又受 `sizeFoot` 的副作用影响，还带一条 400ms 过渡。任何时候要用它的几何，都得先确认这三件事都已经落定。**

### 2026-09-02 定时节点不再替用户定时间

**改了什么**：定时节点的标题从「每天 08:00 增量运行」改成「每天定时增量运行」，cron 那行标上「默认时间，用户未指定」，证据行改成「时间取默认 08:00 · 可改」，「首次 2026-08-01 08:00」改成「首次 下一次到点」。
